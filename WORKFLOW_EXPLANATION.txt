1. EXECUTIVE OVERVIEW & ARCHITECTURE PRINCIPLES
================================================================================
Travinco is a production-grade, full-stack travel agency platform consisting of:
1. A Public-Facing Web Application:
   Showcases destinations, travel packages, offers, events, photo gallery, travel blogs, and multilingual content (English, Hindi, Malayalam), with an integrated trip planning / enquiry portal and a customer self-service account dashboard.
2. An Internal Admin / CRM / ERP System:
   A protected back-office operational suite for managing packages, destinations, customer leads (enquiries), converted bookings, passenger manifests, payment processing, accounting (income/expenses), WhatsApp broadcast campaigns, staff user accounts, and granular permissions.

Core Architecture Principles:
- Single Database, Strict Separation of Concerns: Customer accounts and Staff profiles are isolated into two separate tables (customer_accounts vs profiles) connected to the same Supabase Auth instance, preventing privilege escalation.
- Database Triggers as Single Source of Truth: Critical business logic such as booking balance calculation, payment totals, WhatsApp opt-in verification, and staff profile creation are handled via PostgreSQL database triggers rather than relying solely on client or server code.
- Zero-Client Secret Leakage: All privileged mutations utilize Next.js Server Actions and Supabase SSR Server Clients. Elevated operations (seed scripts, OTP verification, service functions) use SUPABASE_SERVICE_ROLE_KEY exclusively on the server side with 'server-only' protections.
- Resilient Fallbacks: Email sending (Gmail SMTP / Resend) and WhatsApp API operations (Meta Cloud API vs Mock Provider) fail gracefully without breaking core database transactions.

Automated Database Triggers:
- `handle_new_user()` (migration 009 & 021): Fired on auth.users insert. If metadata indicates `is_customer_signup = 'true'`, it skips creating a staff profile. Otherwise, automatically creates a staff profile with default role `sales_staff`.
- `handle_new_customer()` (migration 021): Fired on auth.users insert. If `is_customer_signup = 'true'`, creates a record in `customer_accounts`.
- `recalc_booking_balance` (migration 004 & 024): Automatically recalculates `total_amount = (base_amount - discount_amount) + tax_amount`, updates `balance_amount = total_amount - amount_received`, and sets `payment_status` ('paid', 'partial', 'pending').
- `sync_booking_amount_received` (migration 004): Fired whenever a payment is inserted, updated, or deleted. Automatically updates `amount_received` on the associated booking.
- `trg_campaign_recipient_requires_optin` (migration 006): Enforces at the database layer that no contact can be added to a WhatsApp campaign recipient list unless `opt_in` is true.

4. AUTHENTICATION & ACCESS CONTROL DUAL-TIER MODEL
================================================================================

The system enforces a dual-tier authentication architecture over Supabase Auth:

1. Staff / Admin Tier (`profiles` table):
   - Roles:
     * `super_admin`: Unlimited access to all modules, financial data, and staff user management/permissions.
     * `admin`: Full operational and financial access; cannot manage super_admin settings or users.
     * `sales_staff`: Access to packages, destinations, enquiries, bookings, customers, and marketing.
     * `accounts_staff`: Restricted access focused on income, expenses, payments, and financial reports.
   - Enforcement:
     * App Level: `requireProfile()` in `src/lib/supabase/auth-helpers.ts` checks active status and profile existence. If an active session belongs to a customer account rather than a staff profile, it signs them out immediately and redirects to `/login?reason=not_staff`.
     * Database Level: Migration 010 establishes PostgreSQL RLS policies where `is_staff()` and `is_admin()` functions check `public.profiles`.

2. Customer Tier (`customer_accounts` table):
   - Access:
     * Access to public pages, trip booking requests, and `/account/**` routes.
     * Views only their own booking history and payment receipts (matched via email linkage).
   - Enforcement:
     * App Level: `requireCustomer()` in `src/lib/supabase/customer-auth-helpers.ts` checks the session against `customer_accounts`.
     * Database Level: Explicit RLS policies in migration 021 allow customers to select their own account, bookings, and payments based on `auth.uid() = id` and email matching.

5. DETAILED END-TO-END SYSTEM WORKFLOWS
================================================================================

--------------------------------------------------------------------------------
5.1 Public Visitor Discovery & Browsing Flow
--------------------------------------------------------------------------------
1. Landing Page (`/`):
   - Visitor arrives at the homepage. The page statically renders with a 120-second revalidation period.
   - The hero section renders a 4-panel split collage of published destinations.
   - Visitor can search destinations via `HeroSearch`, view "Snapshot of Our Packages", read travel guides, and view customer reviews.
   - Visitor can toggle the site language between English, Hindi, and Malayalam via the `LanguagePicker`.
2. Exploring Destinations (`/destinations` & `/destinations/[slug]`):
   - Visitor browses all active destinations.
   - Clicking a destination displays destination information and all associated tour packages.
3. Exploring Packages (`/packages` & `/packages/[slug]`):
   - Visitor filters packages by category (Family, Honeymoon, Adventure, Luxury, Budget), duration, or budget.
   - On the package page, the visitor sees:
     * Overview and key highlights.
     * Day-by-day itinerary with accommodation, meals, and transport details.
     * Inclusions and Exclusions checklists.
     * Photo lightbox gallery and YouTube/Vimeo video embeds.
     * Frequently Asked Questions accordion.
     * Dynamic price breakdown (Base price vs Discounted/Special Offer rate).
     * Terms & conditions.

--------------------------------------------------------------------------------
5.2 Customer Account Registration & Booking Tracking Flow
--------------------------------------------------------------------------------
1. Registration (`/account/signup`):
   - Customer submits Full Name, Email, and Password.
   - Server action `signUpCustomer` enforces:
     * Email must strictly be a `@gmail.com` address.
     * Password must contain at least 7 characters, an uppercase letter, a lowercase letter, a number, and a symbol.
   - User is created in Supabase Auth with metadata `{ is_customer_signup: 'true' }`.
   - The database trigger `handle_new_customer` automatically writes a row into `customer_accounts` and ignores `profiles`.
2. Login (`/account/login`):
   - Customer logs in with credentials via `logInCustomer`.
   - Middleware refreshes session cookies.
3. Customer Dashboard & Trip Tracking (`/account/bookings`):
   - Customer navigates to "My Bookings".
   - `requireCustomer()` validates the customer session.
   - System queries `bookings` and `enquiries` linked to the customer's email address.
   - Converted bookings and ongoing enquiries are presented with simplified, friendly statuses:
     * Confirmed / Partially Paid / Fully Paid -> "Confirmed" (Green badge)
     * Lost / Cancelled -> "Rejected" (Red badge)
     * New / Contacted / Follow-up / Pending -> "Processing" (Amber badge)

--------------------------------------------------------------------------------
5.3 Public Enquiry & Lead Submission Flow (Anti-Abuse & Rate-Limiting)
--------------------------------------------------------------------------------
1. Submitting an Enquiry (`EnquiryForm` on Package or Booking page):
   - Visitor fills in Name, Email, Phone number (with country code), Travel Date, Headcount (Adults, Children, Infants), Budget, and Message.
2. Authentication Gate:
   - If the visitor is not logged in, the form prompts them to Log in or Sign up first so they can track their enquiry.
3. Server-Side Protection (`submitEnquiry` in `src/app/(public)/actions.ts`):
   - Rate Limiting: An in-memory IP rate limiter limits submissions to 3 requests per 10 minutes per IP.
   - Honeypot Field: A hidden `website` field traps automated bots; if filled, the action returns simulated success without writing to the database.
   - Validation: Validated using `enquiryFormSchema` in Zod.
4. Database Insertion:
   - Written to the `enquiries` table using the service-role client.
   - Status defaults to `new`, priority defaults to `medium`, source set to `website`.
   - A unique reference number (e.g., `ENQ-XXXX-XXXXX`) is generated.
5. Email Notifications:
   - Asynchronous call to `notifyAdminOfEnquiry` alerts agency administrators via Resend / SMTP.
   - Failure of the email notification does not block the customer enquiry confirmation.

--------------------------------------------------------------------------------
5.4 Lead/Enquiry CRM Management & Follow-up Flow
--------------------------------------------------------------------------------
1. Lead Reception (`/admin/enquiries`):
   - Staff views newly arrived enquiries with color-coded status badges and urgency indicators.
2. Lead Inspection (`/admin/enquiries/[id]`):
   - Staff inspects customer contact information, requested destination, travel dates, passenger breakdown, and messages.
3. Lead Assignment & Workflow Status:
   - Staff can assign the enquiry to a specific team member (`assignEnquiry`).
   - Staff updates workflow status (`new` -> `contacted` -> `follow_up` -> `quotation_sent` -> `negotiation` -> `confirmed` / `lost`).
4. Scheduling Follow-ups:
   - Staff schedules follow-up calls, WhatsApp messages, emails, or meetings (`scheduleFollowup`).
   - The enquiry's `next_followup_date` is updated, and activities are logged in `enquiry_activities`.
5. Customer Decision (Accept / Reject):
   - Staff can click "Accept Enquiry" (`acceptEnquiry`): Status updates to `confirmed`, and an automated notification email is sent to the customer via Gmail SMTP.
   - Staff can click "Reject Enquiry" (`rejectEnquiry`): Status updates to `lost`, an internal rejection reason is logged, and a respectful rejection email is sent to the customer.

--------------------------------------------------------------------------------
5.5 Lead-to-Booking Conversion Flow
--------------------------------------------------------------------------------
1. Conversion Initiation:
   - On an enquiry with a linked package, staff clicks "Convert to Booking" (`convertEnquiryToBooking`).
2. Customer Record Resolution:
   - System checks if a customer record with the enquiry's phone number already exists in `customers`.
   - If not found, a new customer record is automatically generated with source `website`.
3. Pricing & Booking Creation:
   - Base package pricing is fetched.
   - The total price is computed based on adult/child passenger headcount. Staff can specify manual overrides and flat discounts.
   - A new booking row is created in `bookings` with initial status `inquiry`.
   - The enquiry's status is set to `confirmed` and linked to the new booking ID.
   - An activity record `converted_to_booking` is written to `enquiry_activities`.
   - Staff is immediately redirected to the new booking page (`/admin/bookings/[id]`).

--------------------------------------------------------------------------------
5.6 Booking Lifecycle, Passenger Manifest & Payment Processing
--------------------------------------------------------------------------------
1. Booking Details (`/admin/bookings/[id]`):
   - Displays trip travel dates, package name, customer details, financial summary, and passenger list.
2. Passenger Manifest Management (`PassengersPanel`):
   - Staff adds passengers with Full Name, Age, Gender, Passenger Type (Adult, Child, Infant), ID Proof Type (Passport, Aadhaar, National ID), and ID Number (`addPassenger`, `updatePassenger`, `removePassenger`).
3. Payment Logging (`PaymentsPanel`):
   - Staff records a received payment (`recordPayment`) with Amount, Payment Method (UPI, Bank Transfer, Credit Card, Cash, etc.), Payment Date, and Reference Number.
4. Automatic Trigger Sync:
   - Database trigger `sync_booking_amount_received` recalculates `amount_received`.
   - Database trigger `recalc_booking_balance` recalculates `balance_amount = total_amount - amount_received`.
   - `payment_status` automatically transitions (`pending` -> `partial` -> `paid`).
5. Accounting Linkage:
   - When a booking payment is recorded, an identical record is automatically posted into the `income` table under category `package_booking`, maintaining synchronized finance records.
6. Trip Fulfillment:
   - Staff moves booking status from `confirmed` to `completed` once the tour finishes, or `cancelled` if aborted.

--------------------------------------------------------------------------------
5.7 Financial Accounting, Expense Tracking & Analytics Flow
--------------------------------------------------------------------------------
1. Income Ledger (`/admin/income`):
   - Shows all package booking revenues and ad-hoc income (flight bookings, hotel commissions, visa fees, service charges).
   - Staff can add offline income entries using `createIncome`.
2. Expense Ledger (`/admin/expenses`):
   - Operational costs are categorized (Hotels, Transport, Guides, Flights, Office Operations).
   - Staff records vendor bills and tour expenses linked to specific packages or bookings using `createExpense`.
3. Financial Analytics & Reports (`/admin/reports`):
   - Accounts staff and admins view real-time Profit & Loss reports.
   - Filters by Preset Timeframes (Today, This Week, This Month, Last Month, This Year) or custom date ranges.
   - Interactive Recharts bar and line charts break down:
     * Total Revenue vs Total Expenses = Net Profit.
     * Outstanding Booking Receivables.
     * Income breakdown by category.
     * Expense distribution across operational categories.

--------------------------------------------------------------------------------
5.8 WhatsApp Broadcast Campaign & Consent Management Flow
--------------------------------------------------------------------------------
1. Contact Directory & Opt-in Verification (`/admin/whatsapp`):
   - Contacts are stored with phone numbers, display names, tags, and explicit opt-in flags.
   - Legal consent auditing: `opted_in_at` and `opted_out_at` timestamps record consent history.
2. Template Management (`/admin/whatsapp/templates`):
   - Staff creates structured templates with category definitions and message bodies.
3. Campaign Creation (`/admin/whatsapp/campaigns`):
   - Staff creates a campaign, selects a template, attaches optional promotional media URLs, and targets contacts by audience tag.
   - Contacts matching the criteria are added to `whatsapp_campaign_recipients`.
   - The database trigger `trg_campaign_recipient_requires_optin` blocks non-opted-in contacts.
4. Dispatching Campaigns (`sendWhatsappCampaign`):
   - The system calls `getWhatsappProvider()`.
   - In Development/Demo: Uses `MockWhatsappProvider` (simulates realistic latencies, deliveries, and delivery failures without external network costs).
   - In Production: When configured with `WHATSAPP_PROVIDER=meta_cloud_api`, connects to Meta's WhatsApp Cloud API over HTTPS.
   - Recipient statuses update in real time (`pending` -> `sent` / `failed` / `opted_out`).

5.9 Content, Destination, Package & Media Management Flow
--------------------------------------------------------------------------------
1. Package CMS (`/admin/packages`):
   - Draft Creation: Staff creates new packages with title, slug, duration, description, starting rates, and age-banded pricing (Adult, Child, Infant rates).
   - Sub-Resource Editors:
     * Itinerary: Drag-and-drop / day-by-day builder for day title, description, meals, stays, transport.
     * Inclusions & Exclusions: Single or bulk line-by-line entry.
     * Media: Upload package cover photos and tile images directly to Supabase Storage; insert YouTube/Vimeo video embed links.
     * FAQs: Add frequently asked questions per package.
   - Publish Safeguard: The system enforces that a package cannot be published unless it has both a base price and at least one image.
   - Live Preview: Staff previews draft packages on `/admin/packages/[id]/preview` prior to publishing.
2. Destination CMS (`/admin/destinations`):
   - Create, edit, and organize destinations with cover imagery and SEO meta tags.
3. Photo Gallery CMS (`/admin/gallery`):
   - Multi-image file uploads saved to the `gallery-images` bucket.
   - Organized in a two-level hierarchy: Country -> Place/Category.
   - Staff can rename or delete entire gallery folders in a single action.
4. Travel Blog CMS (`/admin/blog`):
   - Articles created with titles, slugs, excerpt snippets, rich content, and cover photos.
5. Special Offers & Events (`/admin/offers`, `/admin/events`):
   - Define promotional discounts (flat amount or percentage) with validity date ranges (`valid_from` to `valid_to`).
   - Active offers dynamically calculate and display discounted prices across package cards and package detail pages.

7. SUMMARY OF AUDIT LOGS, TRIGGERS & INTEGRITY CONSTRAINTS
================================================================================
- Audit Trail: Critical mutations on packages, bookings, and enquiries are logged into `audit_logs` and `enquiry_activities` with actor IDs, timestamps, and before/after payloads.
- Foreign Key Integrity: Child records like itinerary days, inclusions, and package images cascade on deletion (`ON DELETE CASCADE`), while primary destinations and customer associations are protected (`ON DELETE RESTRICT` / `ON DELETE SET NULL`) to prevent orphaned records.
- Financial Accuracy: Booking balances, payments received, and payment statuses are calculated exclusively through database triggers, preventing financial desynchronization.
